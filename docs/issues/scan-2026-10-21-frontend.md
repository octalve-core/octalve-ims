# Scan 2026-10-21 — client-side state and server-rendered pages

Method: static read of `app/**/page.tsx` and layouts (62 pages), `hooks/**`, `lib/react-query/**`, `contexts/**`, `stores/**`, `components/providers/**`, `components/layouts/**`, `components/Pages/**`, `lib/navigation/**`. Not read: `components/admin/*`; the inner logic of most `components/Pages/*`; lines 460 to 655 and 735 to 1816 of `lib/react-query/patch-mutation-cache.ts` (stock, committed and transfer math); products, categories, suppliers, warehouses, user-management, shipping and forecasting hooks only skimmed; list loaders checked only for cache-key scoping. Nothing was run. Findings come from a delegated reviewer (model output); **re-verified** means re-read by the main session on 2026-10-21. Register rows: `README.md`.

## High

**F1. `/admin/my-activity` sends the full user directory to any logged-in role.** (Re-verified: the page checks only `getSession()`, then calls `getUsersForAdmin()`.) `app/admin/my-activity/page.tsx:36` passes every user's email, name, username, role and image as `initialUsers`; `AdminMyActivityContent` also seeds `queryKeys.userManagement.lists()` with it. A client, supplier or retailer who opens the page directly gets it, because `proxy.ts` does no role gating and the sidebar hiding is cosmetic. Fix: `if (user.role !== "admin") redirect("/admin")`, or drop the loader here.

**F2. The ownership check on review detail is inverted.** `lib/server/product-review-detail-data.ts:28` restricts only when `session.role === "admin"`; every other role can load any review by id (reviewer email, linked order and invoice numbers and totals). Used by `app/admin/product-reviews/[id]/page.tsx` and `GET /api/product-reviews/[id]`. Fix: apply the product-owner check to every role.

**F3. The per-entity Redis cache is read before the access check and is not scoped by user or role.** Keys `products:detail:{id}`, `categories:detail:{id}`, `suppliers:detail:{id}` (`lib/cache/cache-utils.ts:241,255,270`); a scope suffix exists only for suppliers (`catalogDetailCacheScope`). `getProductDetailForPage` reads the cache at `product-detail-data.ts:261-266` before role scoping; category and supplier do the same at `:253` and `:240`. Scenario 1: after the owner or an admin or client views product X, any logged-in user who knows the id gets the cached payload for up to 300s. Scenario 2: category and supplier payloads differ by role (clients get `{}` product filter = all owners; others `{userId}`), so whoever fills the cache first poisons it for everyone else. Fix: include role and user id (or an explicit scope) in the key, or authorize first and cache the post-auth result per scope.

**F4. Clients get other buyers' order data in the props of product, category and supplier detail pages.** `getProductDetailForPage` client branch (`product-detail-data.ts:284`) loads all `orderItems` and orders for the product and returns the last 10 as `recentOrders` (order number, totals, payment status, `placedBy` {name, email, image}) plus `statistics.totalRevenue`; the supplier and category loaders do the same for clients (`supplier-detail-data.ts:252,273`; `category-detail-data.ts:265,281`); `ProductDetailPage.tsx:276` renders it for every role. Fix: omit `recentOrders`, `placedBy` and revenue for `client` (and probably `supplier`).

**F5. Mutations are retried once by default, and nothing prevents duplicates.** (Re-verified: `mutations: { retry: 1 }`, `lib/react-query/config.ts:33-37`.) No hook overrides it; a grep for idempotency keys in `lib` and `app/api` found none. A 504 or timeout after the server commits makes `useCreateOrder`, `useCreateInvoice`, `useCreateCheckout`, `useCreateSupportTicket` or a stock transfer re-POST: duplicate order, double stock reserve, two checkout sessions. Validation 4xx also retry and delay the error toast by 1s. Fix: `retry: 0` for mutations; idempotency keys if retries are wanted.

**F6. Silent token refresh bypasses the single-flight helper, and the server revokes the whole session on a race.** `hooks/use-auth-refresh.ts:25` calls raw `fetch("/api/auth/refresh")`, not `refreshAccessToken()` from `lib/auth/refresh-client`; the refresh route treats reuse of a rotated token as compromise and revokes the family. A laptop waking after more than 13 minutes with several tabs: every tab's timer plus the 401 handlers POST the same cookie at once; one wins, the rest hit the reuse path, the user is logged out everywhere. (Plausible, needs runtime check; same as auth A8.)

**F7. Demo credentials, including an admin account, are in the public login bundle.** `LoginPage.tsx:115` imports `lib/auth/test-accounts.ts`, derived from `lib/auth/demo-seed-users.ts`: `test@admin.com` (admin), a client, a supplier and a retailer sharing one `DEMO_PASSWORD`, no env guard. Also remove the hard-coded `test@admin.com` in `lib/server/client-browse-data.ts` (`resolveDefaultBrowseOwnerId`) and `lib/react-query/warm-route-prefetch.ts`. Fix: gate behind a build-time flag so they are tree-shaken in production. (Severity depends on whether production has the demo users.)

## Medium

**F8. Review lists sent to the browser are not filtered.** `getReviewsForProductPage(id, "all")` (`app/products/[id]/page.tsx:25`, `app/admin/products/[id]/page.tsx`) returns every status including rejected and other users' pending reviews with `reviewerEmail`; `ProductReviewsSection.tsx:150-153` filters on the client only, so the full set is in the RSC payload and the query cache.
**F9. Notification optimistic updates use the wrong cache key.** `hooks/queries/use-notifications.ts` (~107-146, 217, 241-248, 316-340) reads and writes the exact key `["notifications","list"]`; `NotificationBell.tsx:45` queries `["notifications","list",{limit:20}]`. The optimistic list update never touches the visible list; the unread badge updates, so badge and list disagree until refetch; `useDeleteNotification.onMutate` creates a stray empty entry. Fix: `setQueriesData` with the prefix.
**F10. Cache patch helpers with `prependIfMissing` also write into non-list arrays.** `patchListCaches(qc, <root>.all, entity, {prependIfMissing:true})` matches every array query under the root: `use-support-tickets.ts:99` prepends a new ticket into `ownerProducts(ownerId)` pickers, reply arrays and the `assigned_to_me` view; `use-product-reviews.ts:167` prepends a pending review into `byProduct(...)` arrays for other products and statuses. Wrong rows show until the invalidate refetch settles. Fix: patch `*.lists()` only.
**F11. Auth state clears on any non-OK session response, and stale localStorage can cause redirect loops.** `utils/auth.client.ts` returns null for 4xx, 5xx and network errors alike; `AuthProvider.checkSession` (`contexts/auth-context.tsx:107,129`) then calls `clearAuthData()`, so a transient 5xx or 429 logs the UI out while the cookie is valid; `HomePage` redirects to `/login`, `/login` redirects back. The 401-refresh-failed paths (`axiosInstance.ts:48`, `lib/api/client.ts:141`, `use-auth-refresh.ts:30`) set `window.location.href="/"` without clearing `isLoggedIn` or `getSession`; `LoginPage.tsx:47-57` then navigates to `/` from stale localStorage and `proxy.ts` bounces back. (Plausible, needs runtime check.)
**F12. Logout hides failures.** `components/layouts/AppShell.tsx:63-80` removes the localStorage keys, then awaits `fetch("/api/auth/logout").catch(() => {})` and navigates to `/login` regardless; a 403 (CSRF), 429 or 500 is ignored, the cookie stays valid and `/login` redirects back; the catch-branch toast is unreachable; the persisted-cache key is removed before the in-memory cache is cleared, so the throttled persister can write it back.
**F13. Persisted cache scoping is weak.** `lib/react-query/provider.tsx:24` persists only roots `auth` and `user`; `auth` is never populated (`useSession` unused), so the only persisted entry is `["user","email-preferences"]`, which has no user id (`config.ts:94`), booleans only, 24h max age, constant buster `"v2.0.2"`. `login()` and the AppShell logout clear it. Not cleared: a session that expires without logout followed by a Google OAuth login (the `prevUserId` check runs only in `checkSession`, which is skipped on `?oauth_success`); a persisted entry beats SSR `initialData`, so user B briefly sees user A's toggles.
**F14. Locale-dependent formatting in server-rendered client components** can cause hydration mismatches: `toLocaleString(undefined, …)` in `ClientPortalPage.tsx:264-350`, `SupplierPortalPage.tsx:193-310`, `BusinessInsightPage.tsx`; `formatStableCurrency`/`formatStableNumber` already exist. (Plausible.)
**F15. No `error.tsx`, `not-found.tsx` or `loading.tsx` anywhere under `app/`.** Only `global-error.tsx` exists; an exception in an SSR loader (`Promise.all` of Prisma/Redis calls, `getAdminCounts` in `app/admin/layout.tsx`) replaces the whole shell; `app/_not-found/page.tsx` is a private underscore folder and is never routed (dead).
**F16. Client-only role gating, and `/admin` layout work for every role.** `app/admin/layout.tsx` calls `getAdminCounts` for any logged-in role (platform-wide `users` and `clients` counts); the sidebar renders User Management, Supplier Portal and Client Portal for `user` and `retailer`, and those pages redirect silently; `ProductDetailPage.tsx:183` sets `isAdminRole = role==="admin" || embedInAdmin`, so any `/admin/...` URL turns on admin UI paths (server checks remain the real gate).

## Low

L1 `use-sync-ssr-query-data.ts:57-90` runs `JSON.stringify` of the full key and data on every render of every list page. L2 `config.ts` has `retry: 3` for all queries, so 403/404 retry for about 7s behind spinners (only `useSession`, `useProduct` special-case it). L3 `patchOrdersOnShipping` (`patch-mutation-cache.ts` ~395) and `mergeRowInArray` spread keys whose value is `undefined`, overwriting cached `trackingNumber`, `trackingUrl` (plausible). L4 `paymentLink` and `trackingUrl` use `z.string().url()` (`lib/validations/invoice.ts:19,44`, `order.ts:92`), which accepts `javascript:` and `data:`; React 19 blocks `javascript:` in `href`, so the risk is phishing links; restrict to http/https. L5 ticket detail pages call `getSupportTicketRepliesForPage(id)` before the access check (result discarded, no leak, fragile); `getProductOwnersForSupport()` sends every product owner's email to every role. L6 dead code: hooks `useSession`, `useLogin`, `useRegister`, `useLogout`, `useNotification`, `useGetShippingRates`, `useStockAllocations`; `AuthContext.logout`; the CRUD actions of `stores/product-store.ts`; `queryKeys.invoices.byOrder`; the `oauth_callback` cookie (set, never read, so no open redirect); stale "Navbar"/"AdminSidebar" comments. L7 `components/shared/ErrorBoundary.tsx` shows `error.message` to end users in production.

## Checked and clean
