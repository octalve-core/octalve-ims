# Scan 2026-10-21 — orders, stock, invoices, payments, shipping

Method: static read of `prisma/order.ts` (and `order.core.ts`, identical except it skips the Stripe refund, so every `order.ts` finding applies to it too), `prisma/invoice.ts`, `prisma/stock-allocation.ts`, `lib/orders/*`, `lib/stock-allocation/*`, `lib/products/*`, `lib/payments/*`, `lib/stripe/*`, `lib/shippo/*`, `lib/invoices/*`, and the order, invoice, stock, payment and shipping routes. Nothing was run. Findings come from a delegated reviewer (model output); **re-verified** means re-read by the main session on 2026-10-21. The race findings assume overlapping requests, which the webhook plus return-page flow produces by design. Register rows: `README.md`.

## Critical

**M1. Stripe payments can be credited more than once.** (Re-verified: "already applied" compares only against the single latest `stripePaymentIntentId`, written after the charge is applied in separate non-transactional writes.) `lib/payments/confirm-checkout-session.ts:81-83, 88-107, 150-152`; `prisma/invoice.ts:214-236`; `app/api/payments/confirm-session/route.ts`. `amountPaid` is read then written, not incremented; no Stripe event or session ids are stored.
- Failure A: the webhook and the SSR return page (`reconcileStripeReturnBeforeDetail`) fire within about a second; both read a null PaymentIntent, both apply a $50 charge: `amountPaid` 100 on a $100 invoice that is half paid, invoice marked paid, order fulfilled.
- Failure B: pay partial session A, then partial session B; B overwrites the stored id; revisiting the A return URL, or POSTing `{sessionId: cs_A}` to confirm-session, re-applies A. Alternating replays pays an invoice off for free.
- Ownership: confirm-session and the `?payment=success&session_id=` page do not check the session belongs to the caller, or to that order or invoice.
- Fix: a `ProcessedPayment(sessionId @unique)` table; in one `$transaction`, insert it and `amountPaid: {increment}`; skip on unique violation; verify ownership and metadata.

**M2. The Shippo webhook has no authentication** (re-verified). `app/api/shipping/webhook/route.ts:17-70`: anyone can POST `{event:"track_updated", data:{tracking_number, tracking_status:{status:"delivered"}}}`; the buyer knows their own tracking number. The order jumps to delivered or shipped regardless of status (cancelled, unpaid pending), skipping stock fulfilment; out-of-order "transit" events move delivered back to shipped; `findFirst` on a non-unique tracking number can hit the wrong order. Fix: shared secret or signature; forward transitions only; ignore cancelled orders.

**M3. `/api/invoices/reminders` bypass when `INTERNAL_API_KEY` is unset** (re-verified; same as auth A3). No de-duplication; flips invoices to overdue.

## High

**M4. Overselling, and orders left with no reservation.** `prisma/order.ts:93-135, 181, 215`; `lib/products/stock-allocation-order-sync.ts:131-146`. Each line's stock check reads the database; reservations happen after the order row is created, outside a transaction; warehouse reserve is check-then-increment. Failure 1: two concurrent orders for the last 5 units both pass (reserved 10 against quantity 5; confirming both gives -5). Failure 2: one order with two lines of the same product (5+5, only 5 free) passes because the check runs before any reservation. Failure 3: if `reservePendingOrderLines` throws midway the order stays pending with partial or no reservation and the API returns 500. No CHECK constraints stop negative `quantity` or `reservedQuantity`. Fix: one `$transaction`, `updateMany ... where quantity - reservedQuantity >= n` and `count === 1` per line, then create the order; merge duplicate product lines first.

**M5. Double fulfilment or restore from read-then-write status transitions.** `lib/invoices/order-payment-sync.ts:67-100`; `lib/server/order-detail-data.ts:153-188`; `lib/server/invoice-detail-data.ts:209-216`; `prisma/order.ts:572-690, 797-926`. `syncOrderPaymentStatusFromInvoice` reads "pending", writes "confirmed", then fulfils; reachable from the webhook, the return page and confirm-session at once, and from plain GETs (detail loaders call `healInvoiceStatusAfterMoney`, so concurrent GETs write). Two callers both decrement `quantity` and `reservedQuantity`. A double-clicked DELETE increments `product.quantity` twice. Fix: claim the transition with `updateMany({where:{id,status:"pending"}, data:{status:"confirmed"}})` and fulfil only when `count===1`; same for cancel; remove writes from GET paths.

**M6. `updateOrder` has no state machine, and several paths corrupt stock.** `prisma/order.ts:644-667, 699-747`. A: confirmed→pending→confirmed runs `fulfillPendingOrderLines` with no reservation: decrements again and drives `reservedQuantity` negative. B: cancelled→pending→confirmed likewise. C: cancelling via PUT leaves `paymentStatus` "paid"; any later PUT (a notes edit) takes the reactivation branch and decrements stock again. D: reactivation never checks stock (negative quantity); a refunded order can be revived and shipped for free. E: cancelling a delivered order restores stock for goods already delivered. F: PUT cancel does not cancel or refund the invoice and does not set `cancelledAt`. Fix: a transition table in a transaction; route all cancels through one function.

**M7. Refund logic can mark an order refunded when no money was returned.** `lib/stripe/refund.ts:41-45`; `prisma/order.ts:838-858`. `createStripeRefund` treats every `StripeInvalidRequestError` as "already refunded" (bad id, disputed charge, insufficient balance all return null); other errors are only logged; the order is then set "refunded" and the invoice cancelled anyway. Partial payments each have their own PaymentIntent but only the latest is stored: cancelling after two partial payments refunds one and keeps the other while showing "refunded". Fix: match only `charge_already_refunded`; refund every paid PaymentIntent with an idempotency key; set "refunded" only on success or when no money was collected.

**M8. `charge.refunded` webhook is wrong for partial refunds and not atomic.** `app/api/payments/webhook/route.ts:129-217`. A $5 Dashboard refund cancels the whole order and invoice and restores all stock, even shipped goods; it increments `product.quantity` only (warehouse allocations drift); writes are sequential, so a failure after the order update means a retry skips it and stock is never restored; an order already cancelled via PUT (paymentStatus still "paid") gets stock restored a second time. Fix: compare `charge.amount_refunded` with the amount paid; transaction; status claim.

**M9. Shipping routes bypass fulfilment and payment, and let the buyer spend the seller's Shippo money.** `app/api/shipping/tracking/route.ts:72-100`; `app/api/shipping/labels/route.ts:96, 109, 142-155`. The buyer (`order.clientId === session.id`) or any supplier on the order can POST tracking: status "shipped" with no eligibility check on pending, unpaid, cancelled or delivered orders; no stock fulfilled, so a later cancel adds stock never deducted. Labels: the eligibility gate exists, but the buyer can buy labels on the seller's account; a client-supplied `rateObjectId` is never tied to this order's shipment; two concurrent requests both pass the `trackingNumber` check and buy two labels. Fix: seller or admin only; run `canGenerateShippingLabel`; claim the order with a conditional update before purchase.

**M10. The buyer controls tax, shipping and discount, and the total is not clamped** (re-verified: uncapped non-negative numbers, `total = subtotal + tax + shipping - discount`). `prisma/order.ts:174-178`; `lib/validations/order.ts:59-70`. A `discount: 999999` gives a negative total, or 0 if equal to the subtotal; checkout then reports "nothing left to pay". Fix: accept these only from seller roles; clamp to subtotal + tax + shipping; integer cents.

**M11. Any client can read any other customer's order or invoice.** `prisma/order.ts:513-520` (`getOrderByIdForClient` falls back to any order with items); `prisma/invoice.ts:446-458`. `/api/orders/:id`, `/api/invoices/:id`, `/api/invoices/:id/pdf` return addresses, notes, buyer email, `stripePaymentIntentId` and the live `paymentLink`; the GETs also trigger the heal writes of M5. Fix: a redacted DTO for non-owners.

**M12. Cancelled orders and invoices can be paid and revived.** `lib/invoices/order-payment-sync.ts:147` (`if (fullyPaid) status="paid"` runs before the cancelled check); `app/api/payments/checkout/route.ts` (the order branch checks neither `order.status` nor `invoice.status`); `prisma/invoice.ts:551` (`updateInvoice` with `amountPaid` revives a cancelled invoice); `app/api/invoices/[id]/send/route.ts:193` (`markInvoiceAsSent` flips paid or cancelled back to "sent"). Failure: a buyer opens checkout, the seller cancels, the buyer pays; the invoice becomes "paid", `paymentStatus` "paid", the order stays cancelled, nothing refunds. Fix: guard in `applyIncrementalInvoicePayment`; status checks in checkout and confirm.

## Medium

**M13. Overpayment silently absorbed.** `Math.min(totalCents, …)` at `order-payment-sync.ts:138` clamps the credit but Stripe already charged the full amount. Two sessions for the full balance, or the stale `invoice.paymentLink` reused by the send route (about line 100: `!paymentLink` reused with a fixed amount and no `chargeAmount` metadata), charge $100 and $40 more with no refund.
**M14. Stock transfers are not atomic.** `prisma/stock-allocation.ts:189-260`: availability is checked only at create (`:143-186`); `completeStockTransfer` does separate decrement, find, then increment or create. Two 10-unit transfers from a 10-unit warehouse both pass (-10); if the destination create hits the unique key the route cancels the transfer but the source decrement stays, so stock is lost.
**M15. Cancelling a confirmed order with no warehouse pick restores stock to the wrong place** (`lib/products/stock-allocation-order-sync.ts:262-277`): `syncRestoreConfirmedOrderAllocations` skips lines without `warehouseId`, so the greedy allocation decrement is never undone; the stock lands in the "unallocated" pool (`prisma/order.ts:899-914`).
**M16. Errors swallowed per line.** `lib/products/order-stock-reservation.ts:128-151` uses `catch {}`; `order.ts:728-765` only warns; status has already changed, so partial fulfilment goes unnoticed; for a pick line `quantity` is decremented before `fulfillAllocationFromPick` can throw.
**M17. Number generation collides.** Order number: `prisma/order.ts:34-58` = `count(today)+1` with a one-second timestamp; two orders in the same second get the same number and the unique key makes the second return 500. Invoice number: `prisma/invoice.ts:79-100` mixes UTC date with local time and has a check-then-insert gap. Fix: a database sequence.
**M18. Product PUT overwrites quantity from a stale read** (`app/api/products/route.ts:463-505`); hard delete (`:867`) runs `stockAllocation.deleteMany` before `product.delete` outside a transaction; if the delete then fails on the order-item FK the allocations are gone.
**M19. Order creation is not tenant-scoped.** `app/api/orders/route.ts:267`, `prisma/order.ts:93-172`: for non-client roles `storeOwnerUserId = userId`; `createOrder` never compares `product.userId`; a user holding another tenant's product id can reserve that tenant's stock, then PUT `paymentStatus:"paid"` on their own order to decrement permanently; a body `clientId` is accepted without checking it is a client. (Plausible: other tenants' cuids are not guessable.)
**M20. Invoice PUT trusts the client's money fields.** `prisma/invoice.ts:499-580`; `lib/validations/invoice.ts:25-42`: any `status`, `amountPaid`, `total`, `amountDue` ("paid" with `amountPaid` 0; `amountPaid` above total; a cancel that leaves `amountDue` and the order active); deleting an invoice with recorded money leaves the order paid; `total` diverges from `order.total`. Fix: derive status and amounts server-side.

## Low

**M21.** Stripe `successUrl`/`cancelUrl` are only checked as URLs (`checkout/route.ts:279`): redirect to any origin with the session id; the webhook throws on any session that is not `ok` (`webhook/route.ts:~85-92`): a session with no matching metadata gets 500 and endless Stripe retries. **M22.** Notification emails likely never send: `shippingAddressSchema` is a plain `z.object`, so `email` and `name` are stripped on create, and the emails and `/invoices/:id/send` depend on `shippingAddr.email` ("Client email not found"). (Plausible; check against the real UI payload.) **M23.** Money columns are `Float`; `price * quantity` is stored unrounded (for example 19.990000000000002); comparisons are cent-safe, so impact is cosmetic and in reports.

## Not covered

`lib/server/*` enrichment loaders, cache internals, rate-limit storage, `lib/email` and `lib/notifications`; RBAC in `lib/auth/can` (a client with Stock/edit may write any product via `buildStockProductWhere`, unverified); `lib/shippo/server.ts` internals and `resolveShippoLabelAddresses`; import flows; `prisma/rls` and migrations (only grepped for CHECK constraints: none); UI call sites that would show whether buyer-side PUT or DELETE is reachable; tests; Neon pooling and serverless concurrency.
