## Critical

**D1. The email webhook is an open mail relay when QStash is not configured.** (Re-verified: the signature is checked only `if (isQStashConfigured())`.) `app/api/email/queue/process/route.ts:26-56`. Brevo without QStash is a supported setup (`lib/email/queue.ts:68` sends directly). An anonymous POST of `{type:"invoice_email", data:{clientName:"<a href=evil>…", paymentLink:"https://evil"}, recipientEmail:"victim@x"}` sends phishing mail from your Brevo sender. Fix: fail closed (503) without the signing keys; validate `type` and payload. (Plausible, needs runtime check: `url: request.url` may not match the published URL behind a proxy.)

**D2. Invoice reminder auth bypass** (re-verified; same as auth A3 and money M3). The query is global and has no "already sent" marker: each call re-emails every sent/overdue invoice and flips its status. Fix: refuse when the key is unset, `timingSafeEqual`, scope to the admin's own invoices, add `lastReminderAt`.

**D3. Product detail is served from cache before authorization** (same as frontend F3). `lib/server/product-detail-data.ts:261-269`, key `products:detail:{id}`: the role and ownership queries run only on a cache miss. The owner opens product P; any logged-in supplier, retailer or user then gets the full payload (buyer names and emails, revenue, owner and creator emails, image file ids) from `GET /api/products/P` for 300s.

**D4. Category and supplier detail cache keys are not scoped per principal.** `lib/server/catalog-entity-access.ts:82-89`; `category-detail-data.ts:252-283`; `supplier-detail-data.ts:239-287`. Only suppliers get a scope; a client's payload (all owners' products and orders) is cached under `categories:detail:{id}` and then served to admin A, and two admins see each other's filtered payloads. Fix: include role and userId in the scope.

**D5. Destructive scripts have no guard** (same as build B6). Wipe path: `prisma/seed.ts:24`, `scripts/delete-all-data.ts:23`, `scripts/reset-demo-db.ts:68` all call `deleteAllDbData` (`scripts/lib/delete-all-db-data.ts:14`, `deleteMany` on every table); `prisma.config.ts` wires `seed.ts` into `prisma db seed` and `migrate reset`. None checks the host, `NODE_ENV` or a confirmation, and none prints the target host. The local `.env` `DATABASE_URL` is hosted Neon. Seeds then create or overwrite admin `test@admin.com` with the shared demo password (`create-demo-accounts.ts`, `update-demo-user.ts:188-221`). `delete-user.ts:97-104` prints "WARNING" and deletes immediately; its P2003 message is unreachable because there are no FKs, leaving orphaned data; `delete-all-suppliers` leaves `Product.supplierId` dangling; `export-tier.ts:191` runs `fs.rmSync(outDir,{recursive})` on an unvalidated argv path. Fix: allowlist local hosts, require `--yes` plus the typed database name, refuse in production or on Vercel.

## High

**D6. Audit log keeps only 50 rows globally.** `prisma/audit-log.core.ts:14,34-45` (same in `audit-log.ts:8`): every write counts and deletes everything older than the newest 50, across all users and tenants; 50 benign events erase evidence; 3 extra queries per write; the count/delete is racy; `businessId` is never set. Fix: age-based retention.
**D7. Order confirmation goes to an attacker-chosen recipient with unescaped HTML.** `app/api/orders/route.ts:343-380`; `lib/email/templates-order.ts:104,179-181,545,602`; `templates.ts:384`. Recipient, `clientName` and address come from the request's `shippingAddress`; no template escapes anything. Any registered client can place an order with `shippingAddress.email=victim` and `name`/`street` containing `<a href=evil>`, and the platform mails the victim from your domain. Fix: HTML-escape every interpolation, send to the authenticated user's email, allowlist href schemes.
**D8. Rate limiting is spoofable and partly broken.** `lib/api/rate-limit.ts:39-44,64-67` keys on client headers `x-user-id`, `x-real-ip`, `x-forwarded-for`; nothing sets `x-user-id`; `withRateLimit` runs before auth in most routes; rotating the header bypasses every limit (including 5/min register and reset on self-host) and can fill another user's `user:<id>` bucket. `lib/cache/rate-limit.ts:77-102` is non-atomic (zrem, zcard, zadd, expire). Lines 84-90: the Upstash `zrange withScores` result is a flat array, so `oldestEntry[0].score` is undefined and `reset`/`retryAfter` become NaN. Fails open when Redis is down.
**D9. Email failures are never retried, and most opt-outs are ignored.** `brevo.ts:99-137` returns `{success:false}` and never throws; `queue.ts:152-167` only logs on success; `propagateErrors` (`route:56`) never fires, the webhook returns 200 and QStash does not retry: a transient Brevo 429/5xx loses the email. No idempotency key; the `queue.ts:100-107` fallback after a publish timeout can duplicate the email. Preferences are checked only for low-stock and stock-out (`queue.ts:140,174`; `notifications.ts:90,215`): the `orderConfirmations`, `invoiceEmails`, `shippingNotifications`, `orderStatusUpdates` opt-outs do nothing. `brevo.ts:84-85` sends `List-Unsubscribe-Post: One-Click` with a mailto-only URL and `Precedence: bulk` on password-reset mail.
**D10. ImageKit file delete has no ownership check** (same as API item 14). `app/api/products/image/route.ts:105-132`; `imageFileId` and `qrCodeFileId` are exposed to every role in the product detail payload (`product-detail-data.ts:165-167`); POST (upload) is open to every role and trusts the client-supplied `file.type`.
**D11. Product import bugs.** `products-import/route.ts:338-346` calls `checkAndSendStockAlerts(p, undefined, undefined, userId)`: the arguments shift so `userId` lands in `recipientName` and the real `userId` is undefined; preferences are skipped, no in-app notification is created, the recipient becomes the global `BREVO_ADMIN_EMAIL`, and it loops over all the user's products so every low or out-of-stock product emails on every import (flood; one owner's product names go to a global address). `lib/import/parser.ts:37-40` splits on `\n` before handling quotes (multi-line quoted fields throw); any column-count mismatch (`:64-68`) aborts the whole file; `validator.ts:143-148` `toNumber("")` returns 0; no row cap, rows created sequentially under the 60s `maxDuration` can leave `ImportHistory` stuck "processing"; error rows carry `rowNumber: 0`; the "SKU already exists" error reveals other tenants' SKUs.
**D12. Password-reset link is built from the request origin** (same as auth A12). `forgot-password/route.ts:85` uses `request.nextUrl.origin`, not `NEXT_PUBLIC_API_URL`; if the deployment accepts an arbitrary Host (typical self-host) an attacker requests a reset with `Host: evil` and the victim's email carries a link to evil with the valid token. The token upsert invalidates the victim's earlier link; only a per-email limit. Plausible, needs a deployment check.

## Medium

**D13. One cache key, two payload shapes.** `orders:list:v5:{"userId"}` is written by `app/api/orders/route.ts` (adds `trackingCarrier`, `labelUrl`) and by `lib/server/orders-data.ts:203-267` (omits them), neither reader checks the shape: last writer wins. `forecasting:summary:v4:{userId}`: the route writes `aiInsights`, `getForecastingForUser` writes without.
**D14. Product reviews leak to every non-admin role.** `app/api/product-reviews/route.ts:44-55`: all non-admin roles share `productReviews:list:v2:{}` and get `getAllProductReviews()` (`prisma/product-review.ts:47`): every review of every product, every status, with `reviewerEmail` (`enrich-review-catalog.ts:220`). The over-broad query is the root cause; the cache amplifies it.
**D15. Tenancy is decorative.** `businessId` is a nullable column on 8 tables and is never read or written by app code (only the seed and `tenant-prisma.ts`); `prisma/rls/001_enable_rls.sql` is outside `prisma/migrations`, so CI `migrate deploy` never applies it, covers Product only, and `businessId IS NULL OR …` makes NULL rows public; the app uses the unscoped `prisma`; `Product.sku @unique` is global (`catalog.prisma:30`) so store B cannot reuse store A's SKU. Fix: pick the tenancy model, `businessId NOT NULL`, composite unique `(businessId, sku)`.
**D16. Float money.** `sales.prisma:13-17,45-46,63-68`; `catalog.prisma:27`; `ProductSupplier.supplierPrice`. `amountDue = total - amountPaid` (`prisma/invoice.ts:547`) is unrounded, so a ~1e-15 residual satisfies the reminders filter `amountDue > 0` and a paid invoice gets a reminder (plausible). Fix: `Decimal(12,2)` or integer cents.
**D17. No indexes on foreign-key or filter columns** (init migration lines 410-546): OrderItem.orderId/productId/warehouseId; Product.categoryId/supplierId/userId; Order.userId/clientId/createdAt/status; Invoice.clientId; Category/Supplier/ImportHistory.userId; RefreshToken.userId; LoginAttempt.userId; ProductSupplier.supplierId; User.roleId/businessId. Every list query is `where userId`, so these become sequential scans as data grows.
**D18. Dangling references and case-sensitive email.** `Product.supplierId` is NOT NULL with no FK, and `app/api/suppliers/route.ts:265` deletes a supplier that still has products; deleting a user (`user-admin.ts:74`) leaves orders, products, invoices and audit rows pointing at a missing user. `User.email @unique` is case-sensitive and no auth path lowercases it (grep finds none): duplicate accounts, and forgot-password misses mixed-case input. Fix: FKs; `citext` or normalise on write.
**D19. Migration `20260823154825` will fail on any database that already has products.** (Re-verified: the previous migration adds `supplierId` nullable; this one does `ALTER COLUMN "supplierId" SET NOT NULL` with no backfill; Prisma's own header warns it fails on existing NULLs.) That gives P3009 and blocks all later migrations. A fresh, empty database (the planned production one) is unaffected. Also: order dates, `Invoice.dueDate` and `Product.expirationDate` are tz-less `TIMESTAMP` while everything else is `TIMESTAMPTZ`.
**D20. Redis outage behaviour, SCAN cost and metrics bugs.** `redis.ts:341-352`: ioredis has no `commandTimeout` and `maxRetriesPerRequest: 3` with 200/400/600ms backoff costs about 1.2s per command when Redis is down; a request issues 6+ sequential commands; the Upstash SDK retries for about 4s (plausible). `cache-utils.ts:186`: SCAN has no COUNT (default 10); `invalidateAllServerCaches` runs 18 concurrent full-keyspace scans; errors are swallowed (`:198-201`) so a mutation succeeds while stale cache lives up to 300s. `system-metrics.ts:86-99` adds incr+expire per cache read and the expire is reset every time so counters never roll over; line 185 checks `typeof hits === "string"` but both adapters return numbers, so the hit rate is always 0. `redis.ts:394-402` logs a warning on every call when `REDIS_URL` is set on Vercel without Upstash. Rate-limit and metrics keys lack the `octalve-ims:` prefix. User-controlled filters create unbounded key cardinality.
**D21. Logging and Sentry.** `lib/logger.ts:74-127`: in production `logger.error` and `logger.warn` go only to Sentry; with no DSN all errors vanish, no console fallback. Every `logger.warn` becomes an unsampled `captureMessage` ("Redis not available" on every API request, `cache/rate-limit.ts:61`; "Rate limit exceeded for user:forgot-password:<email>" puts an email in Sentry). `sentry.ts:71` `setUser` sends the email (`sendDefaultPii:false` does not cover it); logger contexts are sent as-is (Brevo recipient lists, `brevo.ts:102-106`). `scrubSentryEvent` (`sentry-config.ts:152-161`) removes only lowercase `authorization` and `cookie` headers: no body or query scrub, so `/reset-password?token=` ends up in event URLs, breadcrumbs and replays (plausible).
**D22. CSV formula injection in exports.** `lib/export/excel.ts:123-157` and `Papa.unparse` without `escapeFormulae` in `ProductFilters.tsx:147`, `SupplierFilters.tsx:108`, `CategoryFilters.tsx:107`, `WarehouseFilters.tsx:96`: values starting with `= + - @ \t \r` are written raw; a supplier named `=HYPERLINK(...)` runs when an admin opens the CSV. The xlsx path is safe.
**D23. PDF defects.** `lib/pdf/invoice-generator.ts:73-81` defaults the company to "123 Main St, New York…", "+1 (555) 123-4567" and `billing@stockinventory.com`, and the route (`app/api/invoices/[id]/pdf/route.ts`) never passes company data: every customer PDF shows a placeholder identity and a third-party billing email; `$` is hard-coded; totals and notes are drawn at `finalY+15` with no page-break check; a non-string JSON address field makes jsPDF throw and the route returns `error.message` (`route:123-131`).
**D24. Stale payment link and localhost fallback.** `invoices/[id]/send/route.ts:99-141` creates a Stripe Checkout Session once, stores it in `Invoice.paymentLink` and reuses it forever; Checkout URLs expire in 24h and the amount is frozen; `reminders/route.ts:153` emails that dead link; `send/route.ts:180` falls back to `http://localhost:3000` while other routes use `getApiUrl`.
**D25. Unauthenticated ops endpoints.** `/api/health`, `/api/system-metrics`, `/api/performance`: no session, no rate limit. `health` runs `prisma.user.count()`, ImageKit `GET /v1/files` and Brevo `/v3/account` with live keys on every hit (keeps Neon awake, burns quota) and returns raw `error.message` (database host); `system-metrics` exposes memory and node/platform details; `lib/monitoring/performance.ts` has no writers (dead code).

## Low

**D26. Config.** `validateEnv()` in `lib/env.ts` is never called. Env vars read directly and not declared there: `INTERNAL_API_KEY`, `NEXT_PUBLIC_APP_URL` (hard-coded `octalve-ims.vercel.app` fallback in `layout.tsx:86`), `SENTRY_ORG`/`SENTRY_PROJECT`, `NEXT_PUBLIC_SENTRY_RELEASE`, `VERCEL`. The local `.env` defines `DATABASE_URL` twice (pooled, then direct) and has no `DIRECT_URL`, so the effective URL depends on the loader and a local `prisma migrate` would hit the pooled URL (CI uses `DIRECT_URL` correctly). `getApiUrl`'s `headers().get` branch is dead because `headers()` is async. `reset-demo-db.ts:37` clears Redis only for Upstash env vars, not `REDIS_URL`, so static keys such as `userManagement:list:{}` stay stale. `export-tier` ships `docs/` and the seed scripts (demo credentials) in sellable exports.
