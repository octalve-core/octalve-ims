## Priority scale
| P | Meaning | Examples |
|---|---|---|
| **P0** | Live harm now: data leaking, money lost or wrong, auth bypass on production | a route returning other users' data; a forgeable payment webhook |
| **P1** | Serious flaw that is exploitable or loses data once triggered, not known to be hit yet | oversell race, cross-user cache leak, destructive script runnable against staging |
| **P2** | Real defect with limited blast radius, or a flaw that needs an unusual setup | missing rate limit, unbounded list, raw error text returned |
| **P3** | Cleanup, docs drift, consistency | stale trackers, dead code, comment contradicting code |

"**Live?**" says whether the problem exists on a deployed environment (`yes` / `no` / `unknown`). Nothing here has been checked against staging or production, so it is `unknown` until someone confirms what is deployed (`DEPLOYMENT.md` says only one Neon database exists and it serves as staging).

**Evidence levels:** *Read* = found by reading code (not yet proved); *Reproduced* = a failing test or run exists; *Reported* = from a user or the maintainer. Never mark **Reproduced** without a failing test or run.

## Issue types to look for (the taxonomy — extend it when a new kind turns up)
| Type | What to look for in this app |
|---|---|
| **Authorization / IDOR** | a route with no role check; a role checked "somewhere" but not for *this* owner/supplier/client; ids not checked against the caller's scope; list endpoints returning rows outside the caller's scope; `can()` bypassed by an inline `role ===` check |
| **Authentication / session** | refresh rotation races, CSRF not applied to a cookie-authenticated write, missing rate limit, user enumeration, token handling after reset, OAuth account linking, dev fallbacks reachable in production |
| **Privacy / PII** | lists or details returning emails, addresses, phone numbers to roles that don't need them; PII in logs, Sentry events, URLs, persisted browser cache, third-party LLM prompts |
| **Money / payments** | `Float` money, totals trusted from the client, partial-payment drift, webhooks that double-apply or can be forged, confirm endpoints that don't check ownership, refunds without idempotency |
| **Concurrency / data integrity** | read-modify-write on quantities without a transaction or atomic update, double fulfil/decrement, reserved vs committed drift, work done before a transaction commits, polymorphic ids without constraints |
| **Cache** | Redis or TanStack keys that omit user/role/scope; invalidation that misses a writer; persisted client cache shared across users; stale data after logout |
| **Validation / input** | unvalidated query strings, unbounded pagination or bodies, upload type/size, CSV/Excel formula injection, raw `err.message` returned, free text where an enum belongs |
| **Tier / export** | a file in the wrong bucket; a `.core`/`.pro` variant that drifted from its base; a core hook calling a pro route; something an export ships that should not leave the building (see ADR 0001, 0002) |
| **Migrations / deployment** | RLS or other SQL outside Prisma migrations; destructive scripts that don't check the target database; env validation never called; production workflows that can race |
| **Test gap / test health** | tests that depend on the clock or a live database; a rule with no test that fails when it is broken; CI steps missing (lint, tier export) |
| **Availability / performance** | N+1 queries, unbounded lists, missing indexes, slow transactions, rate-limit gaps on public or expensive routes (AI) |
| **UX / accessibility** | tap targets, focus handling, hydration mismatches, duplicate keys |
| **Docs drift** | trackers that disagree with git or code, "built" claims without a test, ADRs contradicted by code, docs that cite files not in git |

## How this register is used
1. Add an issue the moment one is *suspected* — evidence level **Read** is fine; say so honestly.
2. Keep the table sorted by priority, then date. Update status in place; never delete (use *Won't fix* / *Duplicate of ISS-NNNN*).
3. Fixing is a normal task (design → a test that fails first → fix → docs): link the issue from the task file and set **Fixed** with the commit.
4. Add newly discovered *kinds* of issue to the taxonomy above, and note which earlier issue a new one resembles — a pattern found once usually exists elsewhere.
5. Prioritise by priority, then by blast radius (money and personal data first), then by how cheap the fix is.
